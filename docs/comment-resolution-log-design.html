01 / WHY
当前问题

现在只看到结果，
看不到谁改的、为什么改。

`resolved_at` 只保存当前状态和最后操作人；取消再解决会覆盖历史。访客想说“为什么取消”，只能另起一条根评论，脱离上下文。

02 / RULES
设计原则

日志是状态记录，
讨论挂在日志下。

既保留完整操作历史，又让讨论紧贴触发点；不改变现有根评论、回复、筛选和未读模型。

01 / EVENT

事件表，不塞评论表

解决日志存 `share_comment_events`；日志下的讨论存 `event_replies`，避免被根评论计数和回复树混入。

02 / IDENTITY

记录操作者身份

操作者记录 userId、角色（作者 / 访客）和显示名快照；改名后历史仍可读。

03 / STATE

状态与讨论分离

`resolved_at` 仍是唯一状态源；讨论不反向改变状态，也不会因回复自动重新打开。

04 / THREAD

一层讨论，不套娃

每条状态日志下是一层平铺回复，不继续嵌套；保证移动端可读和数据结构简单。

03 / UI
评论线程设计图

状态行下，
可以接着聊。

状态行使用更小字号和状态点；右侧「回复」展开当前记录的讨论串。输入框只属于这条状态，不占用根评论回复框。

DISCUSSION / 讨论

每条状态都能单独回复

状态行右侧的 `回复` 展开一条平铺讨论串；不嵌套，不占用根评论的回复框。

作者 吴老师 · 标记已解决 ↳ 访客 林晓：我确认一下 ↳ 作者 吴老师：已调整
ROLE / 身份

角色跟随操作者

作者操作显示「作者」，访客操作显示「访客」；不是评论原作者的固定角色。

QUIET / 噪声

不改变根评论计数

状态日志和其回复都不计入根评论数；只在对应状态行显示回复数。

MOBILE / 移动端

就地展开，不跳页

点击状态行「回复」在卡片内展开输入框；发送后保持展开并追加，不打断当前阅读位置。

04 / DATA
数据模型

事件一张表，
讨论一张表。

解决状态仍由 `share_comments.resolved_at` 决定；日志与讨论是附属数据，随评论级联删除。

-- 解决 / 取消解决事件 CREATE TABLE share_comment_events ( id BIGINT UNSIGNED AUTO_INCREMENT, comment_id BIGINT UNSIGNED NOT NULL, share_id BIGINT UNSIGNED NOT NULL, action ENUM('resolved', 'unresolved') NOT NULL, actor_user_id BIGINT UNSIGNED NULL, actor_name VARCHAR(32) NOT NULL DEFAULT '', actor_role ENUM('owner', 'visitor') NOT NULL, created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP, PRIMARY KEY (id), KEY idx_event_comment (comment_id, created_at), CONSTRAINT fk_event_comment FOREIGN KEY (comment_id) REFERENCES share_comments(id) ON DELETE CASCADE ) ENGINE=InnoDB; -- 针对某条解决记录的讨论 CREATE TABLE share_comment_event_replies ( id BIGINT UNSIGNED AUTO_INCREMENT, event_id BIGINT UNSIGNED NOT NULL, actor_user_id BIGINT UNSIGNED NULL, actor_name VARCHAR(32) NOT NULL DEFAULT '', actor_role ENUM('owner', 'visitor') NOT NULL, content VARCHAR(1000) NOT NULL, client_id VARCHAR(32) NOT NULL DEFAULT '', created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP, PRIMARY KEY (id), KEY idx_event_reply (event_id, created_at), CONSTRAINT fk_event_reply FOREIGN KEY (event_id) REFERENCES share_comment_events(id) ON DELETE CASCADE ) ENGINE=InnoDB;

06 / API
接口与实时

一条状态，
一个独立讨论入口。

状态操作沿用现有 PATCH；新增状态回复接口。所有写操作都验证链接、评论、事件归属和登录身份。

RESOLVE / EXISTING
PATCH /api/shares/:token/comments/:id { "resolved": true } // 事务内： // 1. 更新 resolved_at / resolved_by // 2. 插入 share_comment_events // 3. 返回 { comment, activity }
EVENT REPLY / NEW
POST /api/shares/:token/comments/:id/events/:eventId/replies { "content": "好的，我确认一下现场", "clientId": "c-8f2a…" } // 返回 { reply }，广播 comment.event.replied DELETE /api/shares/:token/comments/:id/events/:eventId/replies/:replyId
01校验链接token 有效，评论未删除；事件必须属于该评论。
02校验权限作者或登录访客；评论关闭时访客只读。
03写回复插入 event_replies，带 clientId 幂等。
04广播`comment.event.replied` 带 commentId / eventId / reply。
05渲染按 eventId 定位状态行，就地追加并展开。
07 / PERMISSIONS
权限矩阵

状态操作与讨论
各自受控。

解决权限保持不变；状态讨论沿用“登录 + 评论开放”的回复规则，作者始终可管理。

角色解决 / 取消回复状态记录删除状态回复日志角色

访客（未登录）不可只读不可—
历史匿名评论不可不适用（无事件）不适用—
08 / EDGE
边界与验收

讨论不能
反过来改状态。

状态和讨论解耦，所有实时和删除行为都必须可预测。

COUNT

不计入评论数

事件和事件回复都不进入根评论数、未解决数、我的筛选和画布引脚。

SOUND

状态回复发声

状态回复使用 B 类通知 + S7；作者删除他人状态回复使用危险通知 + S8。

DELETE

随评论级联删除

评论删除时事件和讨论一起删除；删除状态回复只删除该回复。

LEGACY

旧状态无历史

旧已解决评论没有事件时不伪造历史；后续新操作开始记录。

IDEMPOTENT

重复操作不重复写

状态相同直接返回；回复用 clientId 去重，避免双击产生两条。

REALTIME

状态行就地追加

收到 SSE 后按 eventId 找到状态行；保持展开和滚动位置，不重置整个面板。

ACCEPTANCE

① 作者解决访客评论，日志出现且可回复；② 访客回复该日志，作者收到 B 类通知 + S7 并看到同一状态行下的讨论；③ 取消解决再解决，产生两条独立日志和各自讨论；④ 日志/讨论不改变根评论数、不增加画布引脚；⑤ 关闭评论后访客不能新增状态回复；⑥ 删除根评论后事件与讨论全部消失。

09 / DECISIONS
需要拍板

三个细节，
确认后落代码。

其余交互按设计图默认执行；这三个点会影响通知和数据结构。

Q.01 / NOTIFY · CONFIRMED
状态回复要通知

已选：B 类通知 + S7。只通知状态记录作者与根评论作者；自己回复不通知。作者删除他人状态回复使用危险通知 + S8。

Q.02 / NEST · CONFIRMED
一层平铺

已选：一层平铺。所有回复挂在事件下，不继续回复某条状态回复；移动端更清晰，也避免数据无限树。

Q.03 / VISIBILITY · CONFIRMED
最近 3 条常驻

已选：最近 3 条，更多折叠为「展开剩余 N 条」；展开状态只在当前面板保持，不写入场景。

Q.04 / DELETE · CONFIRMED
作者与回复作者可删

已选：作者与回复作者可删，沿用普通评论删除的二次确认；删除不改变解决状态和日志。
